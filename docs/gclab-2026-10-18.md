# GC lab: jsgo's garbage collector and heap (jsgo 22cdf68, Go 1.24.7, PGO)

Status: **sweep, GC tax, heap composition, churn, CPU split and locality are measured.** The
pointer-reduction gains are **estimates** derived from them. Nothing was committed; the hook is
applied only through `go build -overlay` (`build.py`, `hook/`), so translated code is unchanged.

Machine: the 4-vCPU Firecracker VM of the benchmark. It was noisy today: run-to-run spread is
±5–10 %, and a pristine/hook control (`control/`, N=5) found the hook binary at GOGC=100 within
noise of the pristine one (typed-app 7.38 vs 7.32 s; downlevel 5.74 vs 5.48 s).

`off, 10 GiB` is **not** a no-GC bound on this VM: with no reuse every allocation faults in fresh
memory, and page faults are very expensive here (bundle: 24.5 s of system time, wall +86 %;

reuses memory and is the usable "almost no GC" bound.

## 2. GC tax (measured; `pooled.py`: the N=5 sweep plus a paired N=10 series, `taxpair/`)

Tax = wall(GOGC=100) − wall(GOGC=off, Java-RSS budget), median of per-round paired differences,
bootstrap 90 % interval. Gap = stored jsgo − stored warm Java (bench2); the tax is scaled to the
stored jsgo wall.

| Task | N | Wall GOGC=100 (median) | Paired Δ wall s, median [90% CI] | Δ wall % | Δ CPU s (% of CPU) | Stored jsgo / warm Java | Tax share of gap [CI] |
|---|---|---|---|---|---|---|---|
| typed-app | 15 | 7.43 | 0.48 [0.33, 0.83] | 7.1% [4.4, 11.1] | 2.49 (25%) | 7.27 / 4.90 | 22% [14, 34] |
| bundle | 15 | 29.96 | 0.93 [0.27, 1.66] | 3.1% [0.9, 5.6] | 9.40 (24%) | 28.31 / 18.91 | 9% [3, 17] |
| downlevel-simple | 15 | 5.55 | 0.25 [-0.10, 0.50] | 4.7% [-1.8, 9.0] | 1.93 (26%) | 5.35 / 3.54 | 14% [-5, 27] |
| checks-only | 15 | 10.86 | 0.35 [0.18, 0.68] | 3.3% [1.7, 6.3] | 3.22 (22%) | 9.92 / 6.77 | 10% [5, 20] |
| single-100 | 5 | 48.58 | 1.14 [-0.78, 4.19] | 2.3% [-1.6, 8.6] | 18.67 (29%) | 48.58 / 31.69 | 7% [-5, 25] |

**Reading:** the GC costs 22–29 % of jsgo's CPU but only ~3–7 % of its wall time (0.25–1.3 s):
it runs concurrently on otherwise idle cores (assists ≈ 0.01 s, STW < 10 ms; marking is active
11 % of the wall time, from `GODEBUG=gctrace=1`). It explains roughly **10–20 % of the gap to warm
Java** (22 % on typed-app, 9 % on bundle). The rest of the gap is mutator speed. On a loaded
machine (parallel compiles) the 25 % CPU would turn into wall time.

## 3. What is on the heap (measured; heap profiles at memprofilerate=4096, `prof/*/heap-heap`, `ana/`)

Live heap per pass (forced GC after every pass, `prof/*/live-passes.tsv`): typed-app 52 MiB after
parse, **peak 93 MiB after checkTypes**, ~80 MiB through optimization; bundle 128 MiB after parse,
~142–145 MiB in the loop, 159 MiB at toSource (output buffer). **The live heap is 80–96 %
pointerful** (/gc/scan/heap). Total scan work over a run (Σ scannable heap per cycle): typed-app
1.4 GiB, bundle 6.2 GiB.

| AST property lists + node_ext | 12 % | 7 % | 7 % | 4 % | 8 % |

~20 % on typed-app (until typesToColors/the end of checks); collections 10–15 %.

## 4. Locality (measured in situ; `prof/*/locality-locality.tsv`)

Pre-order walk (GetFirstChild/GetNext, as NodeTraversal) of the real `jsRoot` at three points,
against copies of the same tree: contiguous pre-order `[]Node`, freshly allocated in pre-order, and
shuffled. ns per node, min of 21 walks (two rounds):

| Point | nodes | as allocated | contiguous | fresh alloc | shuffled | adjacent-slot steps (as allocated) |
|---|---|---|---|---|---|---|
| typed-app after parse | 230 k | 12.9–14.9 | 8.5–10.6 | 11.6–12.1 | 29–35 | 58 % |
| typed-app mid-loop (inlineFunctions#3) | 80 k | 25.6–29.0 | 8.5–12.7 | 21–27 | – | 37 % (24 % > 2 MiB away) |
| typed-app late (coalesceVariableNames) | 78 k | 27.6–29.3 | 9.0–11.3 | 20–25 | 32–38 | 36 % |
| bundle after parse | 1.11 M | 21.9–24.0 | 17.5–19.1 | 16.4–20.8 | 62–66 | 50 % |
| bundle late (coalesceVariableNames) | 1.09 M | 27.5–32.7 | 9.5–15.6 | 25.5–25.8 | 71–78 | 48 % (10 % > 2 MiB) |

After the passes have churned the heap, the AST costs **~2.5× more to walk than a contiguous
layout**; re-allocating in pre-order through the Go allocator (which refills freed slots) recovers
little. `GetNext` (8–10 % of CPU) + `TraverseBranch` (3 %) are mostly this cache/TLB cost.

## 5. Pointer-reduction candidates, ranked (gains are estimates)

1. **AST in pointer-free arenas** (measured share: 37–89 % of the live heap, ~50–85 % of scan
   work; GetNext+TraverseBranch 11–13 % of CPU). *Change:* allocate Nodes in large chunks that the
   GC does not scan — either noscan on-heap slabs (`[]byte` reinterpreted) or index-based
   `NodeID int32` links in a per-compiler `[]Node` — and move the four heap references out of the
   node: `str` → interned string id (or string bytes in an arena), `jstypeOrColor` → type/color
   id, `propListHead` → index into a prop arena with object values in a side table, `ext` → side
   table. *Disturbance:* the slab variant keeps `*rhino.Node` and every accessor, so it touches only
   rhino.Node, its allocation/clone paths and NodeTraversal (substrate only), but needs unsafe code
   and never frees dead nodes (typed-app allocates ~90 MiB of nodes against ~35 MiB live — acceptable);
   the `NodeID` variant shrinks a node to ~40–48 B and is safe, but changes every pass's
   signatures (mechanical, all of jscomp). *Expected:* −50 to −80 % of GC mark work (≈ 12–20 % of
   CPU), wall −2 to −5 % from the GC tax, plus up to −5 % wall from locality if nodes are kept in
   pre-order (a compacting copy per loop iteration is cheap: a contiguous walk is ~10 ns/node).
2. **Collections churn: jutil LinkedHashMap/LinkedHashSet entries** (31–40 % of allocated bytes;
   10–15 % of the live heap). *Change:* entries as values in a slice with int32 prev/next indices
   (open-addressing index map → slice position), no per-entry object; small maps stay inline.
   *Disturbance:* jutil only (API unchanged). *Expected:* −20 to −30 % of allocations/objects,
   fewer GC cycles in proportion, mallocgc (12–15 % of CPU) down by a fifth to a third: wall −3 to
   −6 %.
3. **Data-flow lattices** (flowSensitiveInlineVariables 21 % of bundle churn; MustDef copies one
   ObjectLinkedHashMap per CFG node). *Change:* lattice = dense `[]int32` def ids indexed by
   variable index (per-function var numbering), copy-on-write or bitsets; CFG nodes in a slice with
   int32 edges. *Disturbance:* DataFlowAnalysis, the 4–5 lattice classes and their passes
   (flowSensitiveInlineVariables, deadAssignmentsElimination, coalesceVariableNames, live vars).
   *Expected:* bundle −10 to −15 % allocation, the worst passes vs warm Java (2.4–2.8×) faster.
4. **Scopes, Vars, References** (8.5–11 % of churn, plus most of the 17–19 % pass-local share:
   child Scopes, Reference, NodeTraversal). *Change:* per-traversal scope/var arenas (vars as values
   in a slice, name→index map), References as values in per-name slices. *Disturbance:* scope
   creators and ReferenceCollector users (several passes). *Expected:* −10 to −15 % allocation.
5. **Types** (21 % of the typed-app peak, short-lived after typesToColors). *Change:* intern
   TemplateTypeMap/property maps, ids for JSType. *Disturbance:* the whole type system.
   *Expected:* small for GC (types die before the optimization loop); lowest priority.
6. **Raise GOGC (no code change):** GOGC=200–400 already halves/quarters GC CPU (25 % → 8–15 %)
   for 1.3–2.6× the RSS, still below Java's; wall −3 to −9 % (sweep).
