## Research swarm context (identical for all research agents)

### The project
jsgo (/home/user/jsgo) is a 1:1 Go port of Google Closure Compiler (Java, v20261015), ~410k lines under internal/: parser (internal/parser, internal/parsing), AST + types (internal/rhino), ~1,000 passes and infrastructure (internal/jscomp), Java collection emulation (internal/jutil), colors (internal/colors). Its default output must stay byte-identical with the Java compiler (including iteration orders: Java HashMap order is emulated, LinkedHashMap insertion order kept). Passes are line-by-line translations operating on a `*rhino.Node` API, so substrate changes that keep that API are cheap; changes that need every pass rewritten are expensive (but not forbidden: there are ~1,200 ported files and upstream rarely changes the substrate). A `--fast_mode` flag exists for deliberately relaxed (but deterministic) semantics.

### The problem
Twenty-two optimization rounds focused on wall time (slabs, arenas, sync.Pools, retained arena chunks, global side tables, unsafe tricks). jsgo is 2-3x faster than Java on the benchmarks, but on larger workloads Go's GC overhead balloons and Java wins: Go pointers are 8 B vs Java's 4 B compressed oops, Go's GC is non-generational (every cycle re-marks the whole live heap, so every long-lived pointer is re-scanned), and allocation costs more. Goals now: (1) peak live heap / RSS and pointer reduction (pointer-free "noscan" memory is nearly free for Go's GC), then allocation volume; (2) code readability/simplicity. Wall-time regressions are acceptable unless catastrophic.

### Current data structures (sizes measured)
- AST: `rhino.Node` 64 B = next, first, parent, previous *Node; typeOrColor unsafe.Pointer (JSType, Color, JSDocInfo or an extension box holding cold properties as a linked list of Node_PropListItem); payload uint64 (double bits or two 32-bit interned string IDs); propFlags uint64 (40 boolean props + small enums + source file id); linenoCharno int32; length uint16; token uint8; kind flags uint8. Allocated from slabs of up to 128 nodes. AST is 32% of typed-full's peak heap (160 MB) and most of the heap in untyped builds. Strings are interned in a global sharded pool with 32-bit IDs.
- Parser: scanner -> parse tree (ParseTree interface-typed nodes, Token structs, SourcePosition {*SourceFile; Offset, Line, Column int} = 32 B, SourceRange {Start, End *SourcePosition}) in per-file arenas -> IRFactory converts to rhino.Node. Source decoded to UTF-16 ([]uint16) for Java semantics. Parse-time peak dominates single-large-file builds.
- JSDoc: JSDocInfo {propertyBits, keysBitset int64; propertyValues any (nil, one boxed value, or []any)}; properties described by an interface with 8 methods; type expressions are rhino.Node trees. 10% of typed-full's peak.
- Types: JSType is a Go interface (~150 methods) emulating the Java class hierarchy; JSTypeBase {self JSType (16 B interface for virtual dispatch), resolveResult JSType, templateTypeMap*, registry*, serial ids, flags} = 64 B; FunctionTypeBase 224 B, NamedType 208 B, EnumType 176 B, InstanceObjectType 152 B, UnionType 128 B; property maps per object type; a registry with many maps. ~15% of typed peak. After type checking, ADVANCED builds convert types to "Colors" (simplified, immutable type summaries with sets of prototypes/properties).
- Scopes: Scope/Var/TypedScope/TypedVar, rebuilt by most passes (Scope{parent, lookupParent, arena, varList []*Var, varHash []uint32, bloom, count}); ReferenceCollector with References and BasicBlocks; complex arena/pool machinery.
- Collections: jutil.LinkedHashMap = slots []{key,value} in insertion order + Go map[K]int index past 8 entries; LinkedHashSet, ObjectLinkedHashMap (custom equality), JavaHashMap (Java HashMap order emulation). Top allocation site and ~7% of peak.
- CFG/data flow: LinkedDirectedGraph with pointer-linked nodes and edges per function; data-flow lattices copied per CFG node.
- GlobalNamespace (qualified-name analysis) Name/Ref objects; per-pass pools and arenas everywhere.

### Peak heap measurements (Linux, t=1)
typed-full (28.5 MB of typed Closure code, ADVANCED): peak live 552 MB, RSS 879 MB, peak during type checking. typed-mega (44.6 MB): live 980 MB, RSS 1.5 GB. bundle-mega (36 MB of UMD libraries, ADVANCED untyped): live 700 MB, RSS 1.3 GB. bundle (one 8.9 MB file): peak during parsing (positions, tokens, UTF-16 text). A staged 35M-node googleapis build reaches ~8.7 GB RSS.
