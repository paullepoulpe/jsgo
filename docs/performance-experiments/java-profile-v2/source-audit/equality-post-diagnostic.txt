InstanceObjectType / InstanceObjectType alternative remains UNIMPLEMENTED.
It accounts for403,478entries(21.648754%). Final InstanceObjectType means cached
unknown state and template getter behavior are fixed. Both resolved and distinct,
with empty left map and both known caches, gives false for normal constructors.
But the original isNominalType() path calls constructor.getReferenceName();
FunctionType is nonfinal, so a custom constructor subclass can observe or throw.
Even exact constructor FunctionType.class alone is insufficient: its inherited
PrototypeObjectType.getReferenceName() can follow mutable ownerFunction when its
className is null. FunctionType.setPrototype() can establish that owner chain.
A strict guard additionally requiring both constructors exactly FunctionType.class
AND both getOwnerFunction()==null would ensure the skipped name queries are pure.
That is more checks/maintenance than the preferred prototype/scalar guard for a
slightly smaller raw pair share, so do not combine it speculatively. It remains an
open separate experiment if the smaller candidate proves useful or insufficient.

Broad instanceof ValueType or ObjectType shortcuts remain rejected: custom
subclasses, proxies, nominal comparisons, unknown cache effects, and mutable template
maps require preserving fallback behavior. No result/cross-request cache is proposed.
