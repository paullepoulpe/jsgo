The completed Java experiments found several correct source simplifications, but no confirmed speedup among the changes discussed here. Removing an allocation or branch does not necessarily remove enough execution cost to improve a whole compile. The observations below come only from completed BigQuery runs; the active library-bundle run was not read.

These are changes in candidate medians relative to a separately rebuilt CONTROL, from one cohort of five measured requests per variant. Each screen passed the six compiler-artifact digest checks. They are descriptive results without independent-cohort confidence intervals.

| --- | ---: | ---: | ---: |

| [Plain-object/scalar equality guard](../reviews/screen-bigquery-control-equality-prototype-scalar-v1/compact-summary.json) | +1.33% | −3.35% | −0.63% |
| [Reference-list initial capacity two](../reviews/screen-bigquery-control-reference-list-two-v1/compact-summary.json) | +3.72% | +1.22% | +0.13% |

The equality CPU median looks more favorable than its elapsed result, but its CPU means differed by only −0.20%. That contrast is another reason to avoid selecting a speed winner from one small cohort. Separately, the NAME traversal screen's preliminary elapsed improvement did not establish a gain in its [three-cohort direct-STOCK confirmation](../reviews/confirm-bigquery-stock-traversal-name-switch-v1/compact-summary.json): the confidence interval included parity, and two cohort ratios were slower.

Profile shares describe where to investigate, not the saving available to a patch. Inclusive samples count a method together with its callees, and the same sample can appear under several methods. Scope creation's 8.91% inclusive share therefore cannot be assigned to one duplicate map lookup. Likewise, the original modified-parameter helper accounts for only 18 of 2,221 CPU samples, or 0.81%, despite 3.75% of sampled allocation weight. Allocation weight is an estimate of bytes, not a measure of CPU time, retained memory, or removable elapsed time. These figures come from the [corrected stock profile](../results/profile-stock-bigquery-steady-v2/targets.tsv); they are not measurements of the modified implementation.

HotSpot mechanisms offer plausible explanations, not demonstrated causes here. Small allocations can be cheap through thread-local allocation buffers; inlining and escape analysis can also reduce source-level call and allocation costs. A source change may alter inlining, branch behavior or generated code size. We did not inspect generated assembly or establish which of these effects determined a screen result. Lower allocated bytes also need not produce proportionally less collection work or lower process peak memory.

The equality guard illustrates the tradeoff. It avoids constructing and entering a checker only for qualifying pairs, while its first condition runs on every call that reaches the nonidentity path. Additional conditions run as earlier ones succeed. The observed allocation reduction was 0.63%; the screen did not isolate the guard's CPU overhead. A large diagnostic count of potentially eligible pairs does not establish their cost or prove that all satisfy the cache/template conditions.

Capacity two removes the default list's first-add growth call and starts with two slots instead of ten, but still allocates an array, now at construction. Lists exceeding two entries can incur additional growth and copying. Those costs could erase short-list savings; the actual list-length distribution was not measured. The observed +0.13% total allocation supports rejecting a claimed allocation win on this screen, without proving a particular distribution or cause.

The shared accumulator is the stronger allocation lead: it removes per-node intermediate sets and their merges without a capacity guess, and total measured allocation fell 2.76%. That remains an allocation observation, not a demonstrated speedup. A separate [unimplemented follow-up](../audits/modified-parameters-saturation-v1.txt) could stop the read-only walk once every possible output name has been found, preserving first-insertion order. Rest markers prevent that condition, and extra checks may cost more than they save when completion never occurs.

Measured-phase compilation continued in some runs after warmup readiness passed. The [predeclared JIT annotations](../MEASURED-JIT-REVIEW-NOTE.md) retain every outcome rather than discarding unfavorable requests. They limit steady-state interpretations; they do not supply a convenient causal explanation for each unsuccessful optimization. Further decisions should use independent measurements of a concrete benefit, with the same compiler behavior and byte checks.
