No optimization has a confirmed speed win at this snapshot. The shared modified-parameter accumulator reduced allocation in both completed workload screens, but its **sole selected v4 confirmation** against published STOCK stopped during cohort 2 because of measured parent memory pressure. The [prespecified protocol](CONFIRMATION-V4-PRESPECIFIED.md), [selection record](SELECTED-V4-CONFIRMATION.md), failed run and [host investigation](environment-preflight/README.md) remain intact. No partial cohort is promoted to a smaller confirmation, and no restart was selected after cache cleanup failed to recover reliable headroom. The ideas below are follow-ups, not additional selected confirmations or performance recommendations.

Further directions remain open:

- **Stop when all modified parameters are known.** The shared accumulator is a monotone subset of the parameter-name set. Once their sizes match, later reads cannot change membership or first-insertion order. Every ancestor must also stop its remaining child loop, and the result must retain accumulator order rather than return formal-parameter order. The existing rest marker prevents saturation for valid JavaScript with rest parameters. Extra checks may outweigh saved suffix walks; the original helper's whole inclusive CPU share was only about 0.81% in the stock profile. See the [source audit](audits/modified-parameters-saturation-v1.txt); no implementation or incremental measurement exists.
- **Reduce repeated AST flag lookups.** A [source-only candidate](candidates/node-hot-prop-summary/README.md) adds a two-flag summary to each immutable property-list suffix. This avoids a Node cache field and invalidation writes: existing head replacement, cloning and removal carry the correct suffix summary. The source and proposed focused probe passed independent source review, and exact patch application/reversal was verified. It has not been compiled, run, layout-measured or benchmarked. Extra work on every property-item construction may outweigh faster reads; existing byte-field padding is not proof of zero object-size growth. The earlier [flag audit](candidates/scope-declare-once/node-flag-alternative.txt) and deferred lazy Node-cache draft remain as historical alternatives. Neither is a performance recommendation.
- **Avoid repeated scope analysis within a valid reuse window.** Reusing an analysis across consumers could remove more work than another small predicate change. NodeTraversal already creates scopes lazily, and memoized scope creation already exists. A useful new case needs evidence of actual duplicate scans plus an explicit lifetime in which AST declarations and parent-scope identities stay valid. Broad caching without that boundary risks stale bindings; another counting pass or cache lookup can erase savings. The [scope follow-up](audits/scope-resize-followup-v1/README.txt) records why current evidence did not justify a larger patch.
- **Reuse a local argument-analysis result.** A [bounded source review](source-audit/argument-analysis-local-reuse.txt) found one possible conditional short-circuit inside argument temporary analysis. The two predicates are not interchangeable, custom analyzer hooks complicate universal call/exception parity, and the profile attributes little work to the eligible path. No candidate was prepared; this is a lower-priority idea rather than another measured opportunity.

Previously tried candidates and their completed results remain in the [overall README](README.md). None of these open ideas should acquire a performance claim from source simplicity, profile rank, or another candidate's result.
