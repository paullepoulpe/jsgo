Instrumentation changes cost: the counters establish execution, not time, allocation or RSS benefits. The small CLI-compatible changes have different boundaries. Color preserves miss behavior, canonical order/IDs, factory isolation and the existing externally owned-map constructor; it adds retained identities until the factory/pass is released. The built-in immutable `Color` has a package-private constructor and the registry copies its mappings, so normal public callers cannot inject an arbitrary mutable Color subclass or mutate the registry after caching. Bitset adds unused lower-triangle bits only; the graph reader still consumes the unchanged upper triangle in the original order. Polyfill entries contain only immutable strings/enums and immutable collections, with failed loads retried, custom tables independent, and one successful default retained per defining classloader. Dynamic resource replacement or unusual per-anchor classloaders are outside that cache's equivalence claim.

FSIV and namespace need special attention before an upstream claim of complete drop-in compatibility. FSIV can skip a pathological failure thrown only by unused backward analysis, such as its iteration limit; delaying that analysis can also change which exceptional operation occurs first. It retains the full variable map and original candidate order, and the first necessary analysis still precedes any successful inline. Namespace preserves ordinary namespace/module/source state and incremental Scope/JSChunk arguments, but a custom `AbstractCompiler.getInput` implementation can observe fewer/later calls, and malformed AST/context failures can occur differently. Its private traversal uses the standard syntactic scope creator with an empty default redeclaration callback, so these are not identified normal-CLI output changes. Existing success-path probes cannot prove arbitrary extension-callback or failure-trace equivalence.

If color and ALL do not confirm, the most plausible new small experiment is **memoizing the immutable Color hash**, after checking its cost in an ordinary Java profile. In the available pinned sources, `Color.java:150` memoizes `subtractNullOrVoid`; generated `AutoValue_Color` adds only that cache, while `$AutoValue_Color.java:156` recomputes the full field-combination hash on every call. A separately tested AutoValue `@Memoized` hash implementation could avoid repeated canonical-map hashing across factories without retaining an additional original-color map. It must preserve the existing hash/equality result and handle safe publication; it adds state to every Color, so object size and cold single-use cases matter. Guava immutable sets already cache some component hashes, and the JIT may make the remaining arithmetic cheap. There is no measured gain, no evidence yet that hash computation dominates, and no implementation in this batch.

A union-only original-color cache is a narrower alternative, but current counters cannot establish its advantage: a singleton hit can also save structural map hashing, while repeated unions may make normalization expensive. First split hits/misses by color kind and quantify normalization/allocation cost in a separate diagnostic capture; then freeze one new hypothesis and use fresh holdouts.
