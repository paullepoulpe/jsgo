# Body-Level Port-Fidelity Audit

Read-only inventory of method-body discrepancies between the Go port and the
Java analog at closure-compiler v20260415. The existing portcheck tool only
scores by method-name overlap; this document records places where a Go method
exists with the right name but its body diverges from the Java logic.

Severity legend:
- **high**: behavioural divergence likely to produce different diagnostics or
  runtime semantics on real inputs.
- **medium**: structural omission that does not currently fire (gated by an
  unimplemented surface) but will diverge when the surface is wired.
- **low**: cosmetic / single-file-vs-multi-file simplification with explicit
  comments and no current behavioural impact.

Note: `internal/jscomp/ir.go` does not exist (rhino owns IR; see
`internal/rhino/ir.go`). Per task instructions, `internal/jscomp/scope.go` was
substituted, but that file is a 7-line stub redirecting to `typedscope.go` —
the audit covers `typedscope.go` (the actual TypedScope.java port).
`internal/jscomp/jsdoc.go` does not exist either (rhino owns JSDocInfo); per
instructions, `internal/jscomp/checkmissingrequires.go` is the substitute.

## File: `internal/jscomp/checkaccesscontrols.go`
Java analog: `com/google/javascript/jscomp/CheckAccessControls.java`

| Method | Discrepancy | Severity |
| --- | --- | --- |
| `Check` / `process` | Go takes a single `script` node and runs one walker pass; Java's `process(externs, root)` runs `CollectFileOverviewVisibility` first to populate `defaultVisibilityForFiles` and then calls `NodeTraversal.traverse` twice (once for externs, once for root). The fileoverview-visibility map is never built in Go, so any logic that consults `defaultVisibilityForFiles` (Java lines 494, 763, 766, 798, 842) silently sees an empty map. | high |
| `cacEnterScope` / `enterAccessControlScope` | Java pushes `bestInstanceTypeForMethodOrCtor(root)` onto `currentClassStack` and increments `deprecationDepth` when `isMarkedDeprecated(root)`. Go increments `cacScopeDepth` and `cacDeprecationDepth`, but does **not** maintain the `currentClassStack` of `ObjectType`s. `checkProtectedPropertyVisibility` (Java 948-971) walks this stack to allow protected access from within the enclosing class hierarchy; Go's stub `cacCheckProtectedPropertyVisibility` cannot perform that check. | high |
| `cacWalk` / Java traversal | Java's `shouldTraverse` calls `primaryAccessControlScopeRootFor(node)` which redirects on `isExtendsTarget(n)` (the extends clause is a secondary root of the parent CLASS scope). Go's `cacWalk` enters/exits scopes only on `FUNCTION`/`CLASS` token match — extends-clause nodes are not promoted to scope roots, so `currentClassStack` semantics for `extends Foo` would be off-by-one even if the stack existed. | medium |
| `cacVisit` / `visit` | Java dispatches through `IdentifierBehaviour.select(node)` and a `PropertyReference` factory (`createPropertyReference`) before calling `checkDeprecation` / `checkVisibility` / `checkConstantProperty`. Go's `cacVisit` switches directly on token (NAME, GETPROP, FUNCTION, CLASS, NEW) and never builds a `PropertyReference`. ES6 constructor-invocation paths (`ES6_CLASS_INVOCATION` → `checkEs6ConstructorInvocationVisibility`) are completely absent. | high |
| `cacCheckTypeDeprecation` | Java reads `n.getJSType().toMaybeFunctionType().getInstanceType()` and reports the type's `toString()` as the message argument; Go uses `cacFunctionName(n)` (the AST-level identifier). When the FUNCTION's JSType disagrees with its lexical name (assigned constructors, `Foo = function() {}`), Java and Go report different names. | medium |
| `cacCheckPropertyDeprecation` | Java resolves `objectType` via `castToObject(dereference(propRef.receiverType()))` — the JSType-resolved receiver, including autoboxing. Go calls `cacFindObjectType(receiver.String_())` which only resolves bare NAME receivers via `scope.LookupNominalType`. Receivers like `this.foo`, `arr[0].foo`, autoboxed primitives, or any chained GETPROP all silently miss. | high |
| `cacCheckNameVisibility` | Java reports `BAD_PACKAGE_PROPERTY_ACCESS` / `BAD_PRIVATE_GLOBAL_ACCESS` based on `AccessControlUtils.getEffectiveNameVisibility`. Go's body has empty `case` blocks for `Private` / `Package` with comments saying "skip"; **no diagnostic is ever emitted**. The method is essentially a no-op. | high |
| `cacCheckPropertyVisibility` | Same pattern: Go computes `vis` and `isOverride` but every visibility branch is an empty stub with a deferred-comment. Java emits `BAD_PRIVATE_PROPERTY_ACCESS` / `BAD_PACKAGE_PROPERTY_ACCESS` / `BAD_PROTECTED_PROPERTY_ACCESS` and handles override-narrowing via `checkPropertyOverrideVisibility`. The `cacCheckPropertyAccessVisibility` helper exists separately but is never called from `cacCheckPropertyVisibility`. | high |
| `cacCheckConstantPropertyGetProp` | Java's `checkConstantProperty` (599-657) handles externs stub declarations (`if (sourceNode.isFromExterns() && propRef.declaration())` — record but don't warn), generic-function-type guard (632-634), structural-type fast-fail with `"unknown location due to structural typing"` message (636-645). Go skips all three branches: externs stubs are treated like real assignments, structural types fall through, and generic functions emit warnings Java suppresses. | medium |
| `cacRecordConstPropertyInit` | Java additionally records the init on the implicit prototype when `type.isInstanceType() && prototype.hasProperty(name)` (Java 686-693). Go records only on `ot`. Re-assignments through `Foo.prototype.bar = …` after `inst.bar = …` will be missed. | medium |
| `cacGetConstPropertyInit` | Java consults both `constPropertyInits.get(type, name)` **and** `constPropertyInits.get(getCanonicalInstance(type), name)` per loop iteration (Java 663-671). Go only checks the row for `cur` directly — canonical-instance dedup is missing, so init records placed on a non-canonical alias of the same type are not found. | medium |
| `cacShouldEmitDeprecationWarningNode` | Java's `canAccessDeprecatedTypes` (1032-1050) covers three cases: deprecation-depth, type-of-this is deprecated, and (for ES5 methods) the surrounding ASSIGN target's type is deprecated. Go's check is `c.cacDeprecationDepth == 0` only — cases #2 and #3 are missing. ES5 methods on `@deprecated` namespaces will fire spuriously. | high |
| `cacShouldEmitDeprecationWarningPropRef` | Java's PropertyReference variant (996-1020) additionally suppresses the warning when `propRef.declaration() && jsdoc.isDeprecated()` (don't warn on the declaration site itself). Go's variant has no equivalent guard. | medium |
| `cacIsLValue` | Java treats `propRef.mutation()` per the PropertyReference contract (assignments, compound assignments, deletions, for-in/of LHS, increment/decrement, destructuring-LHS). Go's switch covers ASSIGN-family, DELPROP, FOR_IN/FOR_OF but **omits INC, DEC, and destructuring** (`ARRAY_PATTERN`/`OBJECT_PATTERN` LHS). Mutations through `++foo.bar` won't trigger the const-property check. | medium |
| `cacFindVarJSDoc` / `cacScanVarJSDoc` | Java looks the variable up via `t.getScope().getVar(n.getString()).getJSDocInfo()`. Go re-walks the entire script AST every time looking for matching declarations. Different name-resolution rules: Go finds the **first textual** declaration; Java uses the **lexically enclosing scope**. Inside nested functions that shadow a global, Go reports JSDoc from the outer name; Java sees only the shadowed local. | medium |
| `cacBestJSDoc` | Java's `NodeUtil.getBestJSDocInfo(n)` walks the parent chain (assignment, var-decl, expr-result) when the node itself has no JSDoc. Go's `cacBestJSDoc` returns `n.JSDocInfo()` directly — the parent walk is missing. `isMarkedDeprecated` and `cacCheckTypeDeprecation` therefore miss the common pattern `/** @deprecated */ Foo.prototype.bar = function() {}`. | high |
| `cacCheckFinalClassOverrides` | Java uses `getSuperClassInstanceIfFinal(ctorType)` which goes through `FunctionType.getSuperClassConstructor()` and that ctor's JSDoc. Go reads `info.BaseType()` (the @extends node from the constructor's own JSDoc) and re-resolves by name. If the @extends is omitted but the JSType chain still has a super-class via inference, Java warns and Go doesn't. | medium |

## File: `internal/jscomp/defaultpassconfig.go`
Java analog: `com/google/javascript/jscomp/DefaultPassConfig.java`

The Go port is a **structural skeleton** with all pass bodies stubbed via
`makeNoopPass` / `makeConditionalPass(… true)` / `makeLoopPass`. The orchestrator
methods exist but their bodies discard most of Java's option-driven branching.

| Method | Discrepancy | Severity |

Both paths return early with **completely different pass sets**; Go falls through to the full checks pipeline regardless. | high |
| `GetChecks` | Java gates roughly 25 pass adds with `if (options.…)` predicates: `getProcessCommonJSModules()`, `isChromePassEnabled()`, `enables(LINT_CHECKS)`, `enables(EXTRA_REQUIRE)`, `enables(MISSING_REQUIRE)`, `getClosurePass()`, `getAngularPass()`, `shouldRewriteModulesBeforeTypechecking()`, `isPolymerPassEnabled()`, `shouldInferConsts()`, `shouldComputeFunctionSideEffects()`, `getCheckTypes()` vs `getInferTypes()`, `enables(ANALYZER_CHECKS)`, `preservesDetailedSourceInfo()`, `shouldRewriteModulesAfterTypechecking()`, `shouldAllowDynamicImport()`, `getCheckSuspiciousCode()`, `getJ2clPass().shouldAddJ2clPasses()`, `disables(CHECK_USELESS_CODE)`/`MISSING_RETURN`, `isTypecheckingEnabled() && (!disables(ACCESS_CONTROLS) ‖ enables(CONSTANT_PROPERTY))`, `getConformanceConfigs().isEmpty()`, `getTweakProcessing().isOn()`, `shouldGenerateExports()`, `getExternExportsPath() != null`, `isChecksOnly()`, `getTypedAstOutputFile() != null`. Go adds **both** unconditionally. Also: Java conditionally adds `whitespaceWrapGoogModules` when `shouldWrapGoogModulesForWhitespaceOnly()`; Go omits this pass. | medium |
| `GetOptimizations` | Missing the `isPropertyRenamingOnlyCompilationMode()` early-exit (Java 488-503, returns 11-pass slim list including `addTranspilationRuntimeLibraries`/`addTranspilationPasses` calls) and the `getSkipNonTranspilationPasses()` bail (Java 505-509, returns empty list). `convertChunksToESModules` gated on `getChunkOutputType() == ES_MODULES`. | high |
| `getEarlyOptimizationLoopPasses` | Java toggles `inlineVariables` vs `inlineConstants` based on `shouldInlineVariables()/shouldInlineLocalVariables()` vs `shouldInlineConstantVars()`; Go always adds `inlineVariables` and never `inlineConstants`. Also Java adds `collapseObjectLiterals`, `removeUnusedCode`, `peepholeOptimizations` only when their respective options are true; Go adds all three unconditionally. | medium |

Once any of those passes get real bodies the constant-true will silently force them to run in modes Java doesn't. | medium |

## File: `internal/jscomp/typedscope.go` (substitute for `scope.go`/`ir.go`)
Java analog: `com/google/javascript/jscomp/TypedScope.java`

| Method | Discrepancy | Severity |
| --- | --- | --- |
| `GetTypeOfThis` | Java covers four cases plus the recursion: global, non-arrow function, **isStaticBlockScope**, **isMemberFieldDefScope || isComputedFieldDefRhsScope** (with `root.isStaticMember()` static/instance branching), else `parent.getTypeOfThis()`. Go covers global, non-arrow function, static-block, then falls through to parent recursion — the **MEMBER_FIELD_DEF / COMPUTED_FIELD_DEF_RHS branch is missing entirely**. Class field initializers see `this` as the parent scope's type instead of the class instance. | high |
| `GetVar` | Java implements 25 lines of qualified-name shadowing logic: `getOwnSlot`, fall through to `super.getVar(rootName)` for the root, then either return `rootVar` (simple), `getParent().getGlobalScope().getOwnSlot(name)` (root undeclared), or `rootVar.getScope().getOwnSlot(name)` (qualified). | `MakeImplicitVar` | Method exists in Java (194-206) returning a `TypedVar` for ARGUMENTS/THIS/SUPER (with `EXPORTS` short-circuit and a global-scope short-circuit). Not present in `typedscope.go`. Implicit-var lookups go through a different path in Go (likely `abstractscope.go`); needs cross-check that the path is equivalent. | medium |
| `HasOwnImplicitSlot` | Java method (208-211): `name != null && !equals(EXPORTS) && name.isMadeByScope(this)`. Not present in `typedscope.go`. May be on the abstract scope; not verified here. | medium |
| `GetImplicitVarType` | Java (213-244) computes per-implicit-var type for ARGUMENTS, THIS, SUPER; the SUPER case dereferences ObjectType, instance-type vs prototype branching, and asserts on EXPORTS. Not visible in the Go file; same as above — likely on an adapter. | medium |
| `GetTypeThroughNamespace` | Java uses `parentType.assertObjectType().getPropertyType(prop)` (asserts the parent is an ObjectType). | `ValidateCompletelyBuilt` | Java uses `Preconditions.checkState(reservedNames.isEmpty(), …)` with a multi-line message and resets reservedNames to `ImmutableSet.of()` for GC. | `visitJsDocInfo` | Java additionally pulls `info.getTypeTransformations().keySet()` into `templateParamNames` (line 220). ## Summary Counts

- **High-severity divergences**: 14 (5 in checkaccesscontrols.go, 6 in defaultpassconfig.go, 1 in typedscope.go, 2 in checkmissingrequires.go, plus `cacBestJSDoc`).
- **Medium-severity divergences**: 22.
- **Low-severity divergences**: 8.

The defaultpassconfig.go file is the heaviest source of body-level divergences:
its orchestrator methods (`GetChecks`, `GetOptimizations`, `GetFinalizations`)
are structural skeletons whose option-gating logic is unimplemented. Once the
underlying passes get real bodies, those skeletons must be re-ported with the
full conditional matrix from Java to avoid running passes in the wrong modes.

The checkaccesscontrols.go file has multiple high-severity divergences in
visibility-checking dispatch (`cacCheckNameVisibility`, `cacCheckPropertyVisibility`)
where the Go bodies are empty stubs with `// skip` comments — the file
**has the methods but emits no diagnostics**.
